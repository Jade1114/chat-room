# 高校类 Discord 教学协作平台范围文档

## 1. 项目定位

本项目最终不是一个普通聊天室，而是一个面向高校组织结构的类 Discord 教学协作平台。

聊天室能力是底座，核心价值在于：

- 基于高校身份与组织关系自动分配频道。
- 通过频道承载全校、院系、班级、课程等不同范围的沟通。
- 在稳定的身份与频道体系之上，再扩展教师作业发布、学生提交、教师收集与处理等教学功能。

## 2. 核心概念升级

当前聊天室原型里的概念需要逐步升级：

| 原型概念 | 目标概念 | 说明 |
| --- | --- | --- |
| 临时展示名 | `User` | 用户不再只是展示名称，而是具备角色和组织归属的身份实体。 |
| 临时聊天空间标识 | `channelId` | 频道不再由用户手动输入，而是系统预设并按权限分配。 |
| 临时聊天空间 | `Channel` | 频道有类型、归属组织、权限范围和业务含义。 |
| 临时进房 | 登录后进入工作区 | 用户先登录，再看到自己可访问的频道。 |

## 3. 最终阶段目标

### 3.1 身份管理

- 支持登录入口放在系统最外层。
- 用户拥有明确角色：学生、教师、管理员。
- 用户拥有组织归属：学校、院系、班级、课程。
- 用户身份决定可见频道、可发言范围和可使用功能。

### 3.2 频道体系

频道采用系统预设为主，而不是用户随意创建。

第一批频道类型：

- 全校频道：面向全校用户。
- 院系频道：面向某个院系用户。
- 班级频道：面向某个班级用户。
- 课程频道：面向选课学生和授课教师。

后续可扩展：

- 教师办公频道。
- 作业讨论频道。
- 项目小组频道。
- 管理公告频道。

### 3.3 权限控制

- 学生只能看到与自己学校、院系、班级、课程相关的频道。
- 教师能看到自己授课课程、关联班级和必要的院系频道。
- 管理员能管理组织、用户和频道。
- WebSocket 连接频道时，后端必须校验用户是否有权限进入该频道。

### 3.4 实时聊天

- 消息绑定 `channelId`。
- 用户只能向自己有权限的频道发送消息。
- 支持用户进入、离开、普通聊天消息。
- 后续再扩展消息历史、在线人数、已读未读、消息搜索等能力。

### 3.5 教学业务

作业功能放在频道和身份体系稳定之后实现。

目标能力：

- 教师在课程频道发布作业。
- 学生提交作业。
- 教师收集、查看、下载、批改、反馈。
- 作业与课程、班级、提交人、截止时间绑定。

## 4. MVP 范围

第一版 MVP 只做主干，不做完整教学业务。

### 4.1 必做

- 模拟登录：选择一个预设用户进入系统。
- 预置高校组织结构：学校、院系、班级、课程。
- 预置频道：全校、院系、班级、课程频道。
- 后端根据当前用户返回可访问频道列表。
- 前端改为类 Discord 侧边栏频道布局。
- WebSocket 消息使用 `channelId`。
- 发送消息前校验用户与频道权限。

### 4.2 暂不做

- 真实注册、密码登录、JWT 鉴权。
- 完整数据库建模和持久化。
- 消息历史持久化。
- 已读未读。
- 私聊。
- 文件上传。
- 作业发布与提交。
- 管理后台。

这些功能不是不要，而是不要抢在频道和身份主干之前做。

## 5. 核心领域模型草案

### 5.1 User

用户身份实体。

建议字段：

- `id`
- `displayName`
- `role`：`STUDENT` / `TEACHER` / `ADMIN`
- `schoolId`
- `departmentId`
- `classId`
- `courseIds`

### 5.2 Organization

组织结构实体。

建议拆分：

- `School`
- `Department`
- `ClassGroup`
- `Course`

MVP 阶段可以先用内存 mock 数据，不急着上数据库。

### 5.3 Channel

频道实体。

建议字段：

- `id`
- `name`
- `type`：`SCHOOL` / `DEPARTMENT` / `CLASS` / `COURSE`
- `organizationId`：频道所属组织 ID
- `description`
- `readonly`

### 5.4 ChannelMember / ChannelPermission

频道权限关系。

MVP 阶段可以先不建显式成员表，而是通过用户组织归属动态计算：

- 全校频道：同 `schoolId` 可见。
- 院系频道：同 `departmentId` 可见。
- 班级频道：同 `classId` 可见。
- 课程频道：课程学生和授课教师可见。

## 6. 近期代码改造顺序

### Step 1：后端领域概念改名

目标：先建立 `Channel` 语义，不急着删完所有旧代码。

- 新增 `Channel`、`ChannelType`、`CurrentUser` 等模型。
- 新增 mock 用户和 mock 频道数据服务。
- 新增接口：`GET /api/me`、`GET /api/channels`。
- WebSocket 链路使用 `channelId`。

### Step 2：前端登录外置

目标：用户先选择身份，再进入聊天主界面。

- 新增登录/身份选择页。
- 登录后保存当前 mock 用户状态。
- 主界面不再输入临时展示名和临时聊天空间标识。
- 左侧展示当前用户可访问频道。

### Step 3：频道聊天接入

目标：真实聊天链路基于 `channelId`。

- WebSocket join 消息携带 `channelId` 和 `userId`。
- 后端校验用户是否能进入频道。
- 前端切换频道时自动断开/加入对应频道。
- 消息区显示当前频道上下文。

### Step 4：在线状态与频道详情

目标：补齐频道侧边信息。

- 频道在线人数。
- 当前频道在线用户。
- 用户加入/离开提示。
- 后续再考虑 Redis 化在线状态。

### Step 5：作业模块预留

目标：在课程频道稳定后接入教学业务。

- 先设计作业模型。
- 再做教师发布。
- 再做学生提交。
- 最后做教师收集、处理和反馈。

## 7. 判断原则

后续开发遇到选择时，按以下优先级判断：

1. 先身份，再频道，再聊天，再作业。
2. 先 mock 跑通主链路，再上数据库和鉴权。
3. 先清楚领域模型，再追求 UI 完整度。
4. 先支持高校组织结构，不做泛用聊天室。
5. 不为了功能数量牺牲主干清晰度。
