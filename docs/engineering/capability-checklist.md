# 工程能力清单

> "会做系统"不是一个模糊的感觉。这份文档把"做系统"拆解为具体的工程能力，每项能力对应一种或多种技术，然后映射到能证明它的场景。
>
> 目标：做完任意几个场景后，你可以在面试中说"我在这几个方面有实战经验"，并且有代码和设计文档支撑。

---

## 一、消息可靠性

不做玩具演示。消息管道要能回答：消息丢了怎么办？消费失败了怎么办？重复了怎么办？

| 能力     | 技术手段                                             | 面试能说什么                                       |
| -------- | ---------------------------------------------------- | -------------------------------------------------- |
| 消息不丢 | RabbitMQ publisher confirm — 确认 broker 收到才返回  | "我用了 confirm 模式，不是 fire-and-forget"        |
| 消费确认 | Consumer manual ack — 处理完才确认，崩溃自动 requeue | "auto-ack 会丢消息，manual ack 保证至少处理一次"   |
| 失败重试 | 指数退避重试，最多 N 次                              | "不是无限重试，避免死循环压垮系统"                 |
| 死信处理 | DLQ — 重试耗尽后进入死信队列，记录日志/告警          | "失败消息不丢弃，进 DLQ 可排查可重放"              |
| 幂等消费 | Redis SETNX 去重 — 同一条消息不会处理两次            | "at-least-once 投递 + 幂等消费 = effectively-once" |

## 二、缓存策略

不是"查不到就查 MySQL"。缓存是一个有 tradeoff 的工程设计。

| 能力         | 技术手段                                                 | 面试能说什么                                               |
| ------------ | -------------------------------------------------------- | ---------------------------------------------------------- |
| 读写策略     | cache-aside — 读缓存未命中回源 MySQL 并回填              | "我知道什么时候该用 write-through 什么时候用 cache-aside"  |
| 缓存失效     | 事件驱动 invalidation — Activity 变更时主动失效          | "不依赖 TTL 猜测，数据变了就主动淘汰"                      |
| 一致性边界   | 明确声明 Redis 是热缓存，MySQL 是 source of truth        | "允许短暂不一致，系统能接受，我也说清楚了"                 |
| 数据结构选择 | Sorted Set 做排行榜、String 做去重/限流、Hash 做对象缓存 | "不是只会 GET/SET，什么时候用 ZADD 什么时候用 HSET 有判断" |
| 穿透防护     | 空结果也缓存短 TTL                                       | "防止恶意查询打穿缓存直击 MySQL"                           |

---

## 三、实时推送

不是简单的"前端轮询"，是真正的 push 架构。

| 能力       | 技术手段                             | 面试能说什么                                                 |
| ---------- | ------------------------------------ | ------------------------------------------------------------ |
| 全双工通信 | WebSocket — 浏览器长连接             | "HTTP 轮询在 Activity 场景浪费带宽且延迟高"                  |
| 跨实例广播 | Redis pub/sub — 多实例部署时消息总线 | "单实例 WebSocket 只能推给直连用户，多实例需要 pub/sub 做桥" |
| 定向推送   | 按 userId 推送，不是群发             | "Feed 更新用群发，发起者通知用定向推送——不同场景用不同策略"  |
| 断线重连   | 前端自动重连 + 重连后补偿拉取        | "不是 '断了就断了'，有重连机制和补偿查询"                    |
| 心跳保活   | 定期 ping/pong 检测死连接            | "TCP 长连接可能假死，心跳做主动探测"                         |

---

## 四、并发安全

不是"加个 synchronized 就行"。要从数据竞争的角度审视整个系统。

| 能力               | 技术手段                                                      | 面试能说什么                                                     |
| ------------------ | ------------------------------------------------------------- | ---------------------------------------------------------------- |
| 线程安全审查       | 遍历所有并发接触点，标注保护策略                              | "不是出了问题才修，是设计阶段就审查"                             |
| 原子操作           | Redis 原子命令（SETNX、ZINCRBY）替代读-改-写                  | "MySQL 的 SELECT-then-UPDATE 在并发下有竞态，Redis 原子操作没有" |
| 锁策略             | synchronized / ReentrantLock（单实例）、Redis SETNX（分布式） | "单实例用 JVM 锁足够，多实例才上分布式锁——不过度设计"            |
| 并发度控制         | RabbitMQ consumer concurrency 参数                            | "并发太高压垮下游，太低吞吐不够，需要压测调参"                   |
| 线程安全的数据结构 | ConcurrentHashMap、CopyOnWriteArrayList                       | "不是所有场景都需要锁，无锁数据结构有适用边界"                   |

---

## 五、一致性工程

不是"所有数据都要强一致"。会做系统的标志之一就是知道"哪里可以不一致"。

| 能力         | 技术手段                                               | 面试能说什么                                                               |
| ------------ | ------------------------------------------------------ | -------------------------------------------------------------------------- |
| 一致性分级   | MySQL 强一致 / Redis 最终一致 / RabbitMQ at-least-once | "不是所有数据都一样对待，我按场景分级"                                     |
| 故障恢复     | 每种故障的恢复路径明确记录                             | "Redis 挂了 Feed 降级查 MySQL，RabbitMQ 挂了事件丢失但核心数据在 MySQL 里" |
| 反熵设计     | 缓存从 MySQL 重建的路径存在且可验证                    | "Redis 全丢了也能从 MySQL 重建，不是不可逆的"                              |
| 最终一致窗口 | 明确声明不一致窗口多大（毫秒/秒级）                    | "用户 A 发活动，用户 B 最多 1 秒后在 Feed 看到——这个窗口是可接受的"        |

---

## 六、系统保护

不是"信任用户"。工程系统必须有自己的防护。

| 能力     | 技术手段                      | 面试能说什么                                                |
| -------- | ----------------------------- | ----------------------------------------------------------- |
| 速率限制 | Redis 滑动窗口 / Token Bucket | "不是简单的固定窗口，滑动窗口更平滑；Token Bucket 允许突发" |
| 多级限流 | IP 级 + 用户级分开            | "防刷不能只靠一个维度，换 IP 和换账号都要考虑"              |
| 优雅降级 | Redis 不可用时功能降级不崩溃  | "不是 try-catch 包一切，降级路径是设计出来的不是撞出来的"   |
| 超时控制 | 外部调用设置合理超时 + 熔断   | "同步等 Redis 超时 100ms，超时就降级，不等死"               |

-- 建议推进顺序

完成所有 6 项能力、5 个场景不现实，也不需要。按性价比排：

| 优先级 | 做什么                        | 覆盖                                                                                             |
| ------ | ----------------------------- | ------------------------------------------------------------------------------------------------ |
| 1      | 场景 1（参与意向 + 实时通知） | 消息可靠性 + 并发安全 + 一致性工程（全覆盖），系统保护（限流+降级），缓存（Sorted Set + String） |
| 2      | 场景 2（热度排序）            | 缓存策略（全覆盖），一致性工程（反熵）                                                           |
| 3      | 场景 4（限流安全）            | 系统保护（全覆盖），可以穿插在场景 1/2 中做                                                      |

如果只做一个，**场景 1 覆盖了 6 项能力中的 5 项**（只缺缓存策略的 cache-aside 和事件驱动失效）。做完它，Redis 的三种数据结构、RabbitMQ 的完整可靠管道、WebSocket 定向推送、并发安全、一致性文档——全部有了。
