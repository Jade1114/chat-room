# Classmate Review Guide

> 这份文档是给同学快速理解和试用 chat-room 的入口。它不要求读源码，重点是理解：这个项目解决什么问题、有哪些用户、怎么跑、怎么验收、怎么反馈 bug。
>
> 文档采用 Frank 的“岗位证据”视角：不要只说我用了什么技术，而要说明我理解了什么场景、交付了什么结果、如何验证质量。

---

## 1. 一句话理解这个项目

chat-room 是一个**社团 / 组织持续发现与参与平台**。

它不是单纯聊天室，而是解决“社团招新日之外很难持续发现和加入组织”的问题：用户可以随时发现组织、查看组织主页和公开活动、加入组织，然后再进入该组织的频道交流。

核心链路：

```text
注册 / 登录
→ 浏览公开组织资源
→ 查看组织主页和公开活动
→ 在兴趣出现时加入组织
→ 获得组织频道访问权
→ 后续实时聊天
→ 刷新后仍能看到历史消息
```

---

## 2. 真实痛点：招新日之外的组织发现

普通聊天室只关心“能不能发消息”。这个项目更关心一个真实校园场景：

> 社团招新日一年一次，持续时间短，信息密度高。很多人当时不感兴趣或没来得及了解；过一段时间突然想加入社团时，又找不到一个稳定渠道查看完整社团资源、公开活动和加入方式。

所以这个项目首先要解决“持续发现与参与”，其次才是“加入后的实时交流”。

所以系统里有三层关系：

```text
Organization 组织：围绕兴趣、身份或活动形成的群体
Membership 成员关系：用户是否已经加入组织
Channel 频道：组织下的交流空间
```

关键规则：

- 公开组织应该像常驻社团展台一样被持续展示，而不是只在招新日出现；
- 未加入组织前，可以看组织主页、成员人数、公开活动和公开频道信息；
- 加入组织后，才可以进入频道聊天；
- Public Square 是平台默认公共组织，新用户默认加入；
- 频道访问权以后端 Membership 为准，不靠前端隐藏。

## 3. 项目想证明什么能力

按 Frank 的观点，一个项目要成为“岗位证据”，需要证明三件事：

### 3.1 理解场景

这个项目不是为了堆技术，而是从一个场景出发：

很多社团资源只在招新日集中曝光。新人当时可能不感兴趣、没时间看完，或者几周后才突然想加入某个社团，却找不到完整入口。组织维护者也缺少一个长期展示组织主页、公开活动和加入方式的地方。

### 3.2 交付结果

当前交付的是一个可运行的 MVP：

- 用户能注册 / 登录；
- 用户能浏览公开组织；
- 用户能查看组织主页；
- 用户能加入组织；
- 用户能在非招新季找到并了解组织；
- 用户能进入已加入组织的频道；
- 用户能实时聊天；
- 消息能持久化，刷新后仍能看到；
- 部署时可以用 Docker Compose 一键启动。

### 3.3 验证质量

项目不是只做到“本地能跑”，而是有手动验收流程：

- 用不同测试用户验证权限；
- 用未加入组织的用户验证能否理解组织并找到加入入口；
- 用两个浏览器窗口验证加入后的实时聊天；
- 用未加入组织的用户验证不能进入频道；
- 用刷新页面验证历史消息；
- 用 Docker 部署验证交付环境。

## 4. 用户画像

### 4.1 普通用户 User

目标：在招新日之外也能发现组织、了解公开活动、加入组织，并在加入后参与聊天。

典型行为：

```text
登录
→ 进入组织发现中心
→ 查看一个组织主页和公开活动
→ 判断是否感兴趣
→ 加入组织
→ 加入后进入频道聊天
```

验收重点：

- 是否能快速理解有哪些组织可以加入；
- 组织主页是否足够帮助判断兴趣；
- 是否知道下一步该点哪里；
- 组织和频道是否容易区分；
- 加入组织前后权限变化是否清楚。

### 4.2 组织维护者 Organizer

目标：维护组织主页、发布活动、引导成员交流。

典型行为：

```text
进入自己维护的组织
→ 查看成员和频道
→ 发布活动
→ 在频道里通知成员
```

验收重点：

- 活动发布入口是否好找；
- 组织主页能不能表达组织存在感；
- 频道是否像组织下的交流空间，而不是孤立聊天室。

### 4.3 平台管理员 Admin

目标：作为平台维护者，验证整体数据、默认组织、测试账号和部署环境。

典型行为：

```text
登录管理员账号
→ 查看 Public Square
→ 进入各组织主页
→ 验证默认数据和权限边界
```

验收重点：

- 初始化数据是否完整；
- Public Square 是否是默认组织；
- 线上环境是否稳定可访问。

## 6. 本地 Docker 一键启动

首次启动或需要重置测试数据时：

```bash
cp .env.deploy.example .env.deploy

docker compose --env-file .env.deploy down -v
docker compose --env-file .env.deploy up -d --build
```

平时重新启动：

```bash
docker compose --env-file .env.deploy up -d --build
```

查看状态：

```bash
docker compose --env-file .env.deploy ps
```

浏览器访问：

```text
http://localhost:3000
```

## 7. 给同学的 20 分钟验收流程

### 7.1 登录和默认组织

使用：

```text
test001 / 123456
```

检查：

- 能否成功登录；
- 左侧是否看到 Public Square；
- 是否能进入 Public Square 的频道；
- 是否能看到历史消息。

### 7.2 组织发现和组织主页

操作：

```text
进入组织发现中心
→ 找到一个未加入组织
→ 点击查看主页
```

检查：

- 是否能理解这个组织是干什么的；
- 是否能看到成员人数、公开活动、公开频道；
- 是否能找到“加入组织”按钮；
- 未加入前频道是否不能直接进入聊天。

### 7.3 加入组织后进入频道

操作：

```text
点击加入组织
→ 进入默认频道
→ 发送一条消息
```

检查：

- 加入后左侧“我的组织”是否更新；
- 是否能进入频道；
- 消息是否能发送；
- 刷新页面后消息是否还在。

### 7.4 两个用户实时聊天

准备两个浏览器窗口，分别登录：

```text
test001 / 123456
test002 / 123456
```

操作：

```text
两个用户进入同一个组织频道
→ test001 发消息
→ test002 观察是否实时出现
→ test002 回复
→ test001 观察是否实时出现
```

检查：

- 是否不刷新也能看到消息；
- 发送者名称是否正确；
- 切换频道后未读提醒是否合理。

### 7.5 权限边界

用 `test001` 验证：

```text
二次元同好会：test001 默认未加入
```

检查：

- 可以查看组织主页；
- 未加入前不能进入频道聊天；
- 直接访问频道 URL 时，应看到“加入组织后才能进入频道”的提示；
- 加入后才能进入频道。

## 8. 反馈方式

请同学反馈时不要只说“有 bug”，尽量按这个格式：

```text
我用的账号：
我在哪个页面：
我想做什么：
实际发生了什么：
我原本期待什么：
截图 / 录屏：
是否能稳定复现：
```

例子：

```text
我用的账号：test001
我在哪个页面：组织发现中心 → 二次元同好会主页
我想做什么：加入组织后进入频道
实际发生了什么：加入按钮点了没反应
我原本期待什么：加入成功，并出现进入频道入口
截图 / 录屏：已附
是否能稳定复现：刷新后仍然可以复现
```

## 9. 当前已知边界

以下不是同学需要重点挑刺的方向，除非它们阻塞主流程：

- 当前每个组织只有一个默认频道；
- 还没有完整私密组织 / 审核 / 邀请制；
- 还没有文件上传、私聊、完整通知中心；
- 活动功能是轻量发布和展示，不是完整报名系统；
- 移动端适配不是当前最优先目标。

同学最应该帮忙看的，是主流程是否顺：

```text
登录
→ 找组织
→ 看主页
→ 加入组织
→ 进入频道
→ 发送消息
→ 刷新后还能继续使用
```
