# Product Engineering Map

> 目的：这不是对外 README，而是从“产品型工程师”的角度重新构造 chat-room 项目的内部设计文档。
>
> 核心问题：先说清楚用户、场景、流程和 MVP 边界，再决定系统功能和技术实现。

## 1. 产品命题

chat-room 不是一个泛用聊天室，而是一个面向高校组织关系的频道协作系统。

它的目标是把分散在 QQ、微信、学习通等工具里的教学通知、课程讨论、作业流转和社团协作，逐步收束到一个基于身份、频道和权限的统一协作空间中。

一句话概括：

> 面向高校场景的类 Discord 教学协作平台，用频道承载学校、院系、班级、课程、社团等不同组织范围内的实时沟通与后续教学协作。

## 2. 核心矛盾

高校协作的真实结构是组织化的，但当前常用工具的承载方式是碎片化的。

具体来说：

- 学校、院系、班级、课程、社团天然有层级和权限关系；
- 但实际沟通常常依赖 QQ 群、微信群、学习通等多个工具；
- 通知需要层层转发，容易造成遗漏、延迟和不可追踪；
- 作业收集依赖学委、中间人或多个平台，教师难以统一查看收集状态；
- 社团信息只在固定招新时间集中曝光，日常活动与组织信息不透明；
- 社交平台和教学 / 工作协作之间存在天然隔阂。

所以，本项目要解决的不是“学生需要聊天”，而是：

> 高校的教学与社团协作需要一个能表达组织关系、频道权限和实时沟通的系统，而不是继续把结构化协作塞进普通社交群。

## 3. 用户角色

### 3.1 学生

学生关注：

- 能看到与自己相关的学校、院系、班级、课程频道；
- 能及时收到学校通知、课程通知、调停课信息、考试信息；
- 能在课程频道中与教师和同学交流；
- 后续能统一查看和提交作业；
- 能查看社团信息和公开活动。

### 3.2 教师

教师关注：

- 能进入自己授课课程相关频道；
- 能向课程学生发布通知；
- 能和学生围绕课程内容讨论；
- 后续能发布作业、查看提交情况、集中下载或处理作业。

### 3.3 管理员

管理员关注：

- 能管理学校、院系、班级、课程等组织结构；
- 能创建和维护频道；
- 能分配频道权限；
- 后续能审批社团、管理公告和组织级通知。

### 3.4 社团负责人 / 社团成员

社团相关用户关注：

- 能展示社团信息；
- 能发布公开活动；
- 能申请加入社团；
- 能在社团频道中讨论活动；
- 后续能由学校相关管理人员审核社团申请与活动。

## 4. 真实场景拆解

### 4.1 教学通知

当前流程常见为：

```text
学校/学院通知
-> 辅导员/班主任
-> 班委/学委
-> 班级 QQ 群 / 微信群
-> 学生自行查看
```

问题：

- 层级多，通知实时性不稳定；
- 转发链路中容易遗漏；
- 难以确认每个学生是否接收；
- 历史通知沉没在聊天记录中，难以追溯。

系统切入点：

> 通过学校、院系、班级、课程频道承载通知，让通知按照组织关系直接触达对应人群。

### 4.2 课程讨论

当前课程讨论常常分散在：

- QQ 群；
- 微信群；
- 学习通评论区；
- 私聊；
- 线下转述。

问题：

- 课程讨论和普通社交信息混杂；
- 不同课程群分散，管理成本高；
- 教师难以集中查看学生问题；
- 学生难以区分正式通知和普通聊天。

系统切入点：

> 每门课程拥有自己的课程频道，课程讨论、通知和后续作业都围绕该频道展开。

### 4.3 作业流转

当前作业流程常见为：

```text
教师发布作业
-> 学委通知学生
-> 学生私发/群发/学习通提交
-> 学委整理或平台汇总
-> 教师查看与下载
```

问题：

- 中间人过多；
- 提交状态不透明；
- 教师难以及时知道谁未交；
- 作业文件分散；
- 作业和课程讨论割裂。

系统切入点：

> 在课程频道稳定后，扩展作业发布、提交、收集和状态查看，让作业流转直接绑定课程、学生和教师。

### 4.4 社团活动

当前社团信息常常只在招新季集中出现。

问题：

- 学生日常难以发现全校有哪些社团；
- 社团活动传播依赖朋友圈、群聊或海报；
- 活动信息不统一；
- 加入和审核流程不清晰。

系统切入点：

> 后续通过社团页面和社团频道展示社团信息、公开活动和申请流程。

## 5. 当前 MVP 边界

当前阶段不要试图一次性做完整校园平台。

MVP 只证明一件事：

> 基于高校身份和组织关系，系统可以返回用户可访问的频道；用户只能进入有权限的频道，并能在频道内实时聊天，系统维护频道在线状态。

### 5.1 当前 MVP 做什么

- Mock 用户身份；
- 学校、院系、班级、课程等基础组织数据；
- 频道模型：学校频道、院系频道、班级频道、课程频道；
- 根据用户身份返回可访问频道；
- WebSocket 加入频道；
- 加入频道前校验权限；
- 频道内实时聊天；
- Redis 维护频道在线状态；
- RabbitMQ 处理聊天消息发布与分发；
- 前端以类 Discord 侧边栏展示频道和聊天区。

### 5.2 当前 MVP 暂不做什么

- 真实注册 / 密码登录 / JWT；
- 完整组织管理后台；
- 作业发布与提交；
- 社团申请与审批；
- 私聊；
- 文件上传；
- 历史消息持久化；
- 已读未读；
- 全量通知系统；
- 完整权限管理 UI。

这些不是不要，而是不能抢在“身份 -> 频道 -> 权限 -> 实时聊天 -> 在线状态”主干之前。

## 6. 系统主链路

当前主链路应当收束为：

```text
选择 Mock 用户身份
-> 前端请求当前用户信息
-> 后端返回用户角色和组织归属
-> 前端请求可访问频道列表
-> 后端根据用户身份和频道 scope 过滤频道
-> 用户点击频道
-> 前端建立 WebSocket 连接
-> 前端发送 USER_JOIN，携带 userId 和频道 ID
-> 后端校验用户是否有频道权限
-> SessionManager 绑定 WebSocket session 与用户/频道
-> Redis presence 记录频道在线用户
-> 用户发送聊天消息
-> 后端使用 session 绑定信息覆盖消息身份
-> RabbitMQ 发布聊天消息
-> RabbitMQ Consumer 消费消息
-> 后端广播给当前频道内在线 WebSocket session
-> 前端更新聊天时间线
-> WebSocket 断开时清理 SessionManager 和 Redis presence
-> 后端广播用户离开事件
```

这条链路是当前项目最重要的工程证据。

## 7. 技术选择与场景问题映射

### 7.1 WebSocket

WebSocket 解决的问题：频道内实时交流。

教学通知、课程讨论和频道聊天需要即时反馈。如果用普通 HTTP 轮询，会增加延迟和请求成本，也不符合实时聊天主链路。

在当前 MVP 中，WebSocket 负责：

- 用户进入频道；
- 用户发送聊天消息；
- 后端广播频道消息；
- 连接断开时触发离开处理。

### 7.2 Redis

Redis 解决的问题：跨请求、跨连接维护频道在线状态。

当前 Redis presence 设计：

```text
channel:presence:{channelId}
  -> Set<userId>

channel:user:sessions:{channelId}:{userId}
  -> Set<sessionId>
```

它要解决的真实问题是：

- 一个频道有哪些用户在线；
- 在线人数应该按 userId 去重，而不是按 WebSocket session 计数；
- 同一用户打开多个标签页时，只算一个在线用户；
- 只有最后一个 session 离开时，用户才真正离线。

当前边界：

- 正常 WebSocket 断开时可以清理在线状态；
- 如果服务进程崩溃，Redis 中可能残留 session 信息；
- 后续可以引入 TTL、心跳或定期清理机制。

### 7.3 RabbitMQ

RabbitMQ 解决的问题：消息接收和消息分发解耦。

当前链路中，WebSocket 收到聊天消息后，不直接完成全部广播逻辑，而是先发布到 RabbitMQ，再由 Consumer 消费并广播。

这样做的价值是：

- 将消息入口和消息分发解耦；
- 为异步处理、削峰和失败处理预留空间；
- 为后续多实例广播、消息持久化或消息审计打基础；
- 可以通过 ACK 向前端反馈消息是否被系统接收。

当前边界：

- 当前还不是完整分布式聊天室；
- Consumer 当前广播的是本节点 WebSocket session；
- 跨节点广播、消息重试、死信队列、持久化等属于后续增强。

### 7.4 MySQL / Mock 数据

当前阶段核心不是完整数据库建模，而是先稳定领域模型。

当前数据重点是：

- User：用户身份、角色、组织归属；
- Channel：频道类型、scope、描述、是否只读；
- Course / Class / Department / School：高校组织结构；
- 用户和课程的关联关系。

MVP 可以允许一部分数据 mock，但领域关系必须清楚。

### 7.5 React 前端

前端解决的问题：让频道协作模型可见。

当前前端不是简单聊天框，而是类 Discord 工作区：

- 左侧展示当前用户可访问频道；
- 中间展示当前频道消息时间线；
- 右侧展示在线用户；
- 用户切换频道时重新进入对应频道。

## 8. MVP 验收标准

当前 MVP 可以按以下标准验收：

- 用户可以选择一个 Mock 身份进入系统；
- 学生只能看到自己学校、院系、班级、课程相关频道；
- 教师可以看到自己授课课程相关频道；
- 管理员可以看到全部频道；
- 用户点击频道后可以建立 WebSocket 连接；
- 后端会在加入频道前校验用户权限；
- 无权限用户不能进入频道；
- 同一频道内多个用户可以实时收发消息；
- Redis 能维护频道在线人数和在线用户列表；
- 同一用户打开多个标签页时，在线人数只计 1；
- 用户关闭最后一个连接后，在线人数减少；
- 聊天消息经过 RabbitMQ 发布、消费后广播；
- RabbitMQ 发布成功时，前端能收到消息接收状态；
- 前端构建通过；
- 后端编译通过。

## 9. 当前不应扩展的大功能

为了保持主干清晰，当前不应急着做：

- 作业模块；
- 社团审批；
- 私聊；
- 文件上传；
- 已读未读；
- 管理后台；
- 完整通知系统；
- 复杂权限 UI。

这些功能都可以作为后续方向，但必须建立在身份、频道、权限、实时聊天和在线状态稳定之后。

## 10. 下一阶段工程推进顺序

### P0：收束产品主线

- 以本文档为项目构造地图；
- 明确当前项目不是普通聊天室，而是高校频道协作系统；
- 确认当前 MVP 只围绕身份、频道、权限、实时聊天、在线状态展开。

### P1：收束代码语义

- WebSocket 协议已统一使用 `channelId`；
- WebSocket 协议已统一使用 `displayName` 表示展示名称；
- Session 映射、广播队列等内部命名已收束为 channel 语义；
- 更新 WebSocket 协议文档。

### P2：强化 Redis presence

- 补充 Redis key 设计说明；
- 解释多 session 去重；
- 说明正常断开和异常残留边界；
- 预留 TTL / 心跳方案。

### P3：强化 RabbitMQ 消息链路

- 解释 bucket queue 的设计目的；
- 明确当前保证和不保证什么；
- 梳理发布失败 ACK；
- 说明跨节点广播是后续边界。

### P4：沉淀轻量验证资产

- 手动验收清单；
- REST API curl 示例；
- WebSocket 手动测试步骤；
- Redis key 检查命令；
- RabbitMQ 管理台检查点；
- 构建验证命令。
